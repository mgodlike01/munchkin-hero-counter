# Размещение рядом с Xray

Если нужен доступ **по IP**, см. [готовую схему Ubuntu + HTTPS на 8443](ip/README.md). Она использует публичный IP-сертификат Let's Encrypt и свободный TCP 80 для выдачи/продления. Это также подходит, если 443 занят `telemt` или другой службой.

Приложение состоит из статических файлов. Ему не нужны backend, база данных, доступ к настройкам Xray или отдельный публичный HTTP-порт. Сначала определите, кто обслуживает HTTPS на VPS. Команды ниже — инструкция для владельца сервера; автоматически к VPS проект не подключается.

## 1. Определить текущую схему

На VPS выполните команды чтения:

```sh
sudo ss -lntup | grep -E ':(80|443|8443|18080)\b'
systemctl is-active xray x-ui nginx caddy
```

Если Docker уже установлен:

```sh
sudo docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

Отсутствие отдельных systemd-служб допустимо: например, панель может запускать Xray сама или в контейнере. Проверьте рабочее VPN-подключение до изменений. Сохраните резервную копию настроек панели/Xray или snapshot VPS у провайдера. Для обсуждения достаточно названий процессов и портов; private key, UUID, пароли панели и полные конфигурации присылать не нужно.

Выберите отдельный свободный поддомен, например `hero.example.com`. Направьте только его A/AAAA-записи на VPS; существующие записи для VPN менять не нужно. Если IPv6 не настроен, не добавляйте AAAA.

## 2. Загрузить приложение

После проверки сборки подготовлены два архива в `artifacts/`:

- `munchkin-static.zip` — содержимое `dist/`, для существующего веб-сервера. Node.js и Docker на VPS не нужны.
- `munchkin-source.tar.gz` — исходники и Docker-конфигурация без `node_modules`, кешей и локальных данных.

Для повторного создания архивов после изменений выполните сборку и команды из раздела «Архивы для VPS» в README.

На компьютере, из PowerShell в папке проекта, загрузите нужный архив по SSH/SFTP. Замените `USER` и `VPS_IP`:

```powershell
scp .\artifacts\munchkin-static.zip USER@VPS_IP:/tmp/munchkin-static.zip
```

Либо для Docker:

```powershell
scp .\artifacts\munchkin-source.tar.gz USER@VPS_IP:/tmp/munchkin-source.tar.gz
```

Используйте отдельный каталог приложения; не распаковывайте файлы поверх каталога панели, Xray, существующего сайта или конфигурации прокси.

## 3А. Существующий веб-сервер: готовые статические файлы

Этот вариант особенно удобен на VPS с небольшим объёмом памяти: сборка уже выполнена на компьютере.

В примере используется новый каталог, который ещё не занят другим сайтом:

```sh
sudo mkdir -p /var/www/munchkin-hero
sudo unzip /tmp/munchkin-static.zip -d /var/www/munchkin-hero
```

Если `unzip` отсутствует, можно распаковать ZIP через файловый менеджер/SFTP. В корне каталога должны оказаться `index.html`, `sw.js`, `manifest.webmanifest`, папки `assets` и `icons`. Для Nginx каталогам нужен доступ на проход, файлам — на чтение; подберите права для пользователя существующего веб-сервера без изменения прав чужих каталогов.

Если порт 443 уже обслуживает обычные HTTPS-сайты через HTTP-модуль Nginx, добавьте отдельный `server` для нового домена, сохранив остальные блоки. Возьмите правила раздачи из `deploy/nginx.conf`, измените `root` на `/var/www/munchkin-hero`, задайте домен и сертификат. Для этого домена нужен доверенный TLS-сертификат. Существующие маршруты VPN и default server не меняйте.

Перед применением используйте `sudo nginx -t`; только при успешной проверке — `sudo systemctl reload nginx`. Reload Nginx обрабатывает существующие подключения постепенно. Этот рецепт не применим автоматически к `stream`/SNI-конфигурации Nginx: там распределение 443 нужно рассматривать отдельно.

Если сайты уже обслуживает Caddy, добавьте в существующий Caddyfile блок с вашим доменом:

```caddyfile
hero.example.com {
    root * /var/www/munchkin-hero
    encode zstd gzip
    @fresh path / /index.html /sw.js /manifest.webmanifest
    header @fresh Cache-Control "no-cache"
    try_files {path} /index.html
    file_server
}
```

Проверьте `caddy validate --config /etc/caddy/Caddyfile`, затем выполните reload существующей службы. Путь и способ перезагрузки должны соответствовать вашей установке. Не заменяйте весь файл этим блоком.

## 3Б. Docker уже установлен: отдельный локальный контейнер

Установка Docker с нуля меняет сетевые настройки и правила фильтрации Linux. Если его ещё нет, для действующего VPN предпочтительнее вариант со статическими файлами и существующим веб-сервером. Не устанавливайте Docker на работающий VPN-сервер вслепую. [Документация Docker о firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

В новом, отдельном каталоге:

```sh
sudo mkdir -p /opt/munchkin-hero
sudo tar -xzf /tmp/munchkin-source.tar.gz -C /opt/munchkin-hero
cd /opt/munchkin-hero
```

Создайте здесь `.env` по образцу `deploy/vps.env.example` с содержимым:

```dotenv
MUNCHKIN_HTTP_PORT=18080
```

Убедитесь по `ss`, что `18080` свободен. При необходимости выберите другой свободный порт и поменяйте его также в HTTPS-прокси. Затем:

```sh
sudo docker compose -p munchkin-hero config
sudo docker compose -p munchkin-hero up -d --build
sudo docker compose -p munchkin-hero ps
curl -I http://127.0.0.1:18080/
```

В `config` должно быть опубликовано **только `127.0.0.1:18080` → контейнерный `80`**. Порты хоста 80/443 проект не публикует. `-p munchkin-hero` отделяет ресурсы приложения от Compose-проектов панели/VPN. На слабом сервере сборка может расходовать заметные CPU/RAM; используйте статический архив, если нельзя нагружать VPS сборкой.

Для существующего HTTPS-прокси подготовлены примеры:

- `deploy/nginx-existing-proxy.conf.example` — отдельный HTTP `server` в уже работающем Nginx, где 443 обслуживает HTTPS, а не `stream`.
- `deploy/Caddyfile-existing-proxy.example` — новый домен в уже работающем Caddy.

Они проксируют на `127.0.0.1:18080` и требуют замены домена/путей сертификатов. Примеры предполагают, что прокси работает на хосте. В контейнере прокси адрес `127.0.0.1` означает сам контейнер; схему сети тогда нужно подобрать отдельно.

## 4. Если 443 занимает непосредственно Xray / REALITY

Новый Nginx/Caddy не сможет одновременно слушать тот же IP:443. Новый поддомен сам по себе не устраняет конфликт портов. Оставьте listener, ключи, SNI, target и маршруты Xray в текущем состоянии.

Варианты без изменения Xray:

1. **Отдельный HTTPS-порт**, например `https://hero.example.com:8443`. Сначала проверьте, что 8443 свободен. Для сайта всё равно нужен доверенный сертификат на домен.
2. Отдельный IP или другой хост для сайта, если нужен обычный URL без указания порта.

Для первого варианта есть `deploy/Caddyfile-8443.example`. Это конфигурация **отдельного процесса** Caddy с уже выпущенным сертификатом: автоматические редиректы/выдача сертификатов и admin API отключены; слушается 8443. Нужны доступный бинарный Caddy и сертификат; не заменяйте этим примером работающий Caddyfile и не запускайте установщик, который сам займёт 80/443.

После замены домена и путей можно сначала проверить и запустить отдельный процесс вручную:

```sh
caddy validate --config /opt/munchkin-hero/Caddyfile-8443
caddy run --config /opt/munchkin-hero/Caddyfile-8443
```

Предварительно скопируйте пример в указанный рабочий файл. Для постоянной работы используйте отдельную systemd-службу с собственным именем и путём к конфигурации. Пользователю процесса нужен доступ к сертификату и ключу. Управляйте только этой новой службой.

Сертификат можно выпускать/продлевать через DNS-01 у своего DNS-провайдера либо использовать уже настроенный механизм сертификатов. DNS-01 не требует занимать 80/443. При использовании ручных сертификатов настройте их продление и перечитывание новым процессом. HTTP-01 требует доступного извне **80**, TLS-ALPN-01 — **443**; перенос сайта на 8443 не переносит проверку ACME на этот порт. Не запускайте standalone Certbot с остановкой Xray. [HTTPS в Caddy](https://caddyserver.com/docs/automatic-https), [настройка ручных сертификатов](https://caddyserver.com/docs/caddyfile/directives/tls).

Разрешите только выбранный дополнительный порт TCP в действующем firewall и security group провайдера, не сбрасывая существующие правила. Для работы по HTTP/1.1–2 UDP на 8443 не обязателен. Не включайте/не перенастраивайте firewall целиком ради этого сайта.

## 5. Проверить и обновлять

- Проверьте VPN-подключение тем же клиентом, которым пользовались до размещения.
- Откройте сайт по HTTPS без предупреждений сертификата, дождитесь «Готово к офлайну», установите PWA и проверьте авиарежим.
- Для Docker используйте только команды из каталога этого проекта с `-p munchkin-hero`. Остановка приложения: `sudo docker compose -p munchkin-hero stop app`. Она не управляет Xray.
- Перед обновлением сохраняйте предыдущий каталог/образ для возврата. Статический релиз лучше загружать в новый каталог и переключать сайт на него; старые файлы с хешами оставляйте доступными, пока открытые клиенты завершают обновление.
- Обновление сайта по прежнему адресу не удаляет localStorage игроков. Смена протокола, домена или порта создаёт другой origin: сохранение автоматически туда не переносится. Импорт и экспорт удалены; при смене адреса внесите показатели вручную.

Без вывода занятых портов и сведений о существующем HTTPS-прокси нельзя выбрать один универсальный TLS-рецепт, который гарантированно сохранит все маршруты конкретного VPS. Перечисленные варианты не требуют менять конфигурацию Xray; публичный вход выбирается по фактической схеме сервера.
